# 口吻与站位（第一顺位审查焦点）v9.4

> **这是全技能的第一顺位焦点，排在立意、结构、材料、AI 味之前。**
>
> 理由：一篇立意清楚、结构工整、零 AI 味的稿子，如果口吻错了、站位错了，一句话就能让稿子作废，甚至造成真实的关系损失。文字质量的其他维度都是「不够好」，站位错了是「不能用」。
>
> 判定主体：**主要靠 reviewer 语感判断，脚本只能兜住少量字面形态。** 本焦点的多数问题没有固定词形，grep 天然抓不到，因此 **Polish 模式禁止「只跑脚本就宣布通过」**（见 SKILL §2.2 step 2 与本文 §6）。

## §1 两个前置问题（动笔前必答）

任何写作任务开始前，**先明确回答这两个问题，写进工作记录**。答不上来就先问用户，不要先动笔。

**问题一：读者是谁。**
不是「读者大概是领导」这种模糊回答，要具体到：什么单位、什么层级、什么专业背景、拿这份材料去干什么。
- 「协会信息技术部主任，处级，不懂云计算技术细节，明天要拿这份附件去向分管副秘书长汇报」——这是合格的回答。
- 「客户」——这是不合格的回答。

**问题二：我是谁。**
写稿人的身份和站位。同样要具体到：什么机构、与读者是什么关系、有没有资格下判断、有没有资格提要求。
- 「外部咨询机构，受客户委托做论证，提供依据不替客户决策，无权对客户提要求」——合格。
- 「帮忙写材料的」——不合格。

**两个问题的答案共同决定口吻。** 口吻不是文风偏好，是身份关系的语言投影。身份关系搞错，措辞再讲究也是错的。

**Coach 模式**：立意 checkpoint 之前先过这两问。
**Polish 模式**：step 2 派 reviewer 时，这两问的答案必须写进 reviewer 的 prompt。用户没交代就问用户，**不要替用户假设**。

## §2 站位矩阵：谁对谁说话

| 说话人 → 听话人 | 可以做 | 绝对不能做 |
|---|---|---|
| **外部机构 → 客户** | 陈述事实、给出判断、提供依据、列出可选项、说明利弊 | ①命令式语气（应/必须/不得/需要贵单位/要求）②批评客户既往做法③替客户拍板、替客户定原则④替客户做合规判断⑤显得比客户更懂客户的业务 |
| **下级 → 上级** | 报告情况、提出建议、请示事项、说明困难 | ①替上级定调②越权表态③把建议写成决定④在材料里替上级承诺 |
| **领导 → 下属** | 部署工作、提出要求、肯定成绩、指出不足 | ①让下属读了会多想的话（点名式批评、含沙射影、突然拔高某人）②把工作要求写成情绪表达③夸奖时厚此薄彼 |
| **平级机构 → 平级机构** | 通报、商洽、征求意见 | ①指令口吻②评价对方内部事务 |
| **机构 → 公众** | 说明、告知、答复 | ①内部口径外泄②推诿式表述③居高临下 |

### §2.0 已知假阳：不要拿口吻去改体裁定式

**口吻审查的边界是「作者在说什么话」，不是「体裁要求写什么成分」。** 体裁的必备成分不因口吻焦点而改。

| 假阳 | 为什么不是站位问题 |
|---|---|
| 公文帽子的目的排比「为明确 A，稳妥推进某某单位 B，根据……，现将……说明如下」 | 帽子是固定几何，目的状语交代的是成文缘由，与「谁在说话」无关。详 [`gongwen-format.md`](gongwen-format.md) §十.4 |
| 帽子里的「根据《X 法》《Y 规定》」 | 依据段是帽子必备成分，不是堆砌文号 |
| 帽子里的「结合本单位实际」 | 成文依据的常规表述，不是替客户判断 |
| 必备政治表态、指导思想 boilerplate | 体裁必备，不适用空话可证伪测试（constitution §0.5） |
| 「一是……二是……三是……」列举法 | 党政公文标准句式，不是 AI 三段式 |

**处理**：reviewer 报到这几类，主对话判假阳并驳回，**不得据此改写**。改了会把公文体降成事务性便条，用户会当场驳回。

**边界**：豁免只覆盖体裁定式本身。定式之外的正文出现同型祈使或替客户拍板，仍按下文处理。

### 外部机构对客户：最高频的三类越界

**越界一 · 命令式。**
凡出现「应」「必须」「不得」「要」「需」加在客户身上做主语的句子，一律改为陈述或建议。

| 越界 | 改法 |
|---|---|
| 协会应当在迁移前开展保密审查。 | 迁移前对拟上云的数据和业务开展一次保密审查。（去主语，写成事项） |
| 协会必须选择通过评估的平台。 | 从通过评估的平台中选择，是现行制度的要求。（把要求归还给制度，不是归给我方） |
| 建议协会尽快明确责任部门。 | 责任部门的确定，可结合协会内部分工另行研究。（把决策权交回） |

**要点**：要求可以来自制度、来自文件、来自同业做法，**就是不能来自我方**。写「制度要求如此」，不写「我们要求你如此」。

**越界二 · 批评既往。**
「目前尚未建立」「现有做法存在不足」「一直没有明确」这类表述，即使属实，也会让客户读了不舒服，且往往是在批评坐在对面那个人的工作。

| 越界 | 改法 |
|---|---|
| 协会目前尚未建立数据分类分级制度。 | 数据分类分级的相关工作，可在本次迁移中一并推进。（把缺口写成机会） |
| 现有系统的运维权限管理比较粗放。 | 运维权限的边界，在上云后由合同条款进一步明确。（把问题写成下一步） |
| 之前的方案没有考虑到这一点。 | 这一点在本轮论证中一并纳入。（不提「之前」） |

**要点**：**缺口写成下一步，不写成过失。** 需要指出问题时，把时间轴指向未来，不指向过去。

**越界三 · 替客户判断。**
特别是合规判断、法律判断、涉密判断。咨询机构可以列依据、摆事实、说同业怎么做，**不能替客户下「这样做是合规的」这种结论**。

| 越界 | 改法 |
|---|---|
| 该方案符合保密法要求。 | 保密法及其实施条例对此的规定是……同类机构的做法是……（摆依据，结论留给客户） |
| 上云不涉及国家秘密，因此不存在合规风险。 | 按现行规定，工作秘密与国家秘密分属两类，管理要求不同。（陈述规范，不下风险结论） |

## §3 口吻六检

Polish step 3 第 ① 维逐句过一遍。

1. **祈使检**：全文搜「应」「必须」「不得」「要求」「需」，逐个确认主语是谁。主语是读者方 = 越界。
2. **既往检**：全文搜「尚未」「目前没有」「缺乏」「不足」「一直」「以往」，确认有没有在批评读者的工作。
3. **代客决策检**：全文搜「因此可以确定」「结论是」「符合……要求」「不存在……风险」，确认有没有替读者做本该他做的判断。
4. **多想检**（领导对下属专用）：设想每一个下属读到这句话时会不会对号入座、会不会觉得说的是自己、会不会揣测有别的意思。有一处就改。
5. **谦抑检**：我方在文中出现的次数。外部机构给客户的材料，我方越少出现越好；论证靠依据本身站住，不靠「我们认为」撑着。
6. **温度检**：念一遍。有没有哪句听起来是在教育对方、显摆自己懂、或者急于表功。

## §4 自证清白与自我宣告

> 这一类是 AI 味最隐蔽的形态：每个字都对，连起来是稿子在自言自语。

### §4.1 自证清白（给自己的证据打包票）

证据摆出来，自己会说话。**替证据背书的旁白，一律删。**

| 病句形态 | 实例 | 处理 |
|---|---|---|
| 替证据打包票 | 这两条在官方文件里都能落到白纸黑字。 | 删。后面三条依据自己会说话。 |
| 反复申明来源可靠 | 这不是我们的判断，是文件原文写的。 | 删。引了文号就够了。 |
| 预防性反驳 | 也许有人会问……对此需要说明的是…… | 删。没人提出的质疑不要自己先提。 |
| 强调可核验 | 四条都是**可核验的**正面要求 | 去掉「可核验的」。是不是可核验，读者自己会判断。 |
| 同义反复三遍 | 同一个意思换三种说法说三遍 | 留最准的一句，删其余。 |

**判据**：把这句话删掉，论证是否照样成立？照样成立 = 它没在论证，只在给论证壮胆 = 删。

### §4.2 自我宣告式过渡

文章自己描述自己的结构，是最典型的机器指纹之一。

| 禁 | 改法 |
|---|---|
| 下面从三个方面说明 | 直接写「一是……二是……三是……」 |
| 这一点很重要 / 需要特别指出的是 / 值得注意的是 / 必须强调 | 删。重要就把它放在前面，不靠标签强调 |
| 本文将从 A、B、C 三方面展开 | 删导语，直接进 A |
| 综上所述 / 由此可见 | 删，或换成实质结论句 |
| 具体来说 / 换句话说 | 多数可删；真需要换个说法，说明前一句没写清，回去改前一句 |
| 落到具体平台上两条都能落实： | 具体到平台：（去掉「都能落实」这层自我担保） |

### §4.3 过度防御的段落级形态

- 一个论点后面挂三段「补充说明」，每段都在防一个没人提的反问。
- 每提一个数字就跟一句「这是保守估计」。
- 每引一个文件就跟一句「该文件现行有效」。

**处理**：真有必要交代的，合并成一句放在最后；其余全删。

## §5 语体一致性

> **v9.3 新增，来自 2026-07-28 实战失误。** 一篇党政公文风格的稿子里，一半小标题是规范的事项名，一半是口语设问和论证旁白，脚本全部放行，因为它们不含任何黑词。

### §5.1 run-in 小标题必须是事项名

run-in 小标题指 `**XXX。**` 后接正文的粗体标签。**它是标题，不是句子。**

规范：**名词性短语**，2 至 12 字，不带主谓完整结构，不带疑问，不带口语。

| 病 | 正 |
|---|---|
| **谁评。** | **评估主体。** |
| **怎么评。** | **评估流程。** |
| **评完管多久。** | **有效期与持续监督。** |
| **名单本身写着政务云。** | **公告名单所载的平台名称。** |
| **政府采购文件里也这么叫。** | **政府采购文件中的称谓。** |
| **司法部的政务云是租的，不是自建的。** | **司法部政务云的取得方式。** |
| **这套系统装的信息与中注协基本相同。** | **该系统承载的信息。** |
| **两种形态都有同类先例。** | **两种形态的先例。** |
| **法律和行政法规怎么规定工作秘密。** | **法律和行政法规的规定。** |

**三条判据**：
1. 有没有谓语动词构成完整判断？有 = 它是句子不是标题。
2. 是不是疑问？是 = 改成对应的名词（谁评 → 评估主体）。
3. 它说的是「这一段讲什么」，还是「这一段的结论是什么」？说结论 = 把结论移到正文首句，标题只留事项名。

**同级对仗**：同一节下的 run-in 标题字数和结构要接近。一组里出现 2 字、4 字、13 字混排 = 要改。

### §5.2 章节标题的语体（区别于 gongwen-format §三的排版规范）

`gongwen-format.md` §三管的是**排版**（编号、字体、缩进）。本节管的是**措辞**。

一级标题（一、二、三）规范：
- **名词短语，2 至 6 字为宜**，同级对仗。
- 禁冒号（「三、制度依据：从保密法到 14 号文」→「三、制度依据」）。
- 禁疑问句式（「四、能不能上政务云」→「四、承载平台」）。
- 禁悬垂「的」字尾（「五、可以参照的实践」→「五、实践依据」）。
- 禁「之一 / 之二」式编号补丁。
- **禁泄露我方工作过程**：「现场备问」「答辩预案」「补充调研发现」这类内部工作阶段的名称不能上标题，改成读者视角的事项名（「现场备问」→「常见问答」）。

好的一组（实例，2026-07-28 中注协附件）：

```
一、总体结论
二、上云范围
三、制度依据
四、承载平台
五、实践依据
六、保护措施
```

六个二字词，同级对仗，读者扫一眼就知道全篇骨架。

### §5.3 正文口语渗入

党政公文与咨询报告里，下列表述一律不得出现。这些词单看不是黑词，放进这个体裁就是轻佻。

- **大头在这里** / 大头是 / 主要就这些
- **算谁的** / 归谁管 / 各管一头
- **差在哪里** / 好在哪儿
- **到底有没有** / 还做不做 / 能不能行
- **出了事** / 万一出问题（改：发生安全事件时）
- **摆出** / 抛出 / 甩给
- **说白了** / 简单讲 / 换个说法
- **这块** / 那一块 / 这一摊
- **不外乎** / 无非是

改法一律是换成同义的书面表述，**不是删句子**：

| 病 | 正 |
|---|---|
| 大头在这里，大部分措施由服务商落实。 | 此类事项数量最多，大部分措施由中标服务商落实。 |
| 责任算谁的，合同里写清楚。 | 责任划分由合同条款明确。 |
| 出了事谁负责。 | 发生安全事件时的责任承担。 |

### §5.4 铁律：不得为过软阈值而降低语体

> **来源：2026-07-28 实战失误，性质严重。**

`scan-ai-taste.sh` 的软阈值（「这一」≤2、「核心」≤3 等）是**近似指标，不是写作目标**。为了让某个计数降下来，把规范的书面表述换成口语（把「这一部分」改成「大头」），是**用工具指标换文风质量**，方向完全错误。

**正确做法**：软阈值超标时，改的是「这一部分内容较多」这类空转句式本身——删掉它，或换成实质表述（「此类事项数量最多」）。**降密度靠删空话，不靠降语体。**

reviewer 遇到疑似为凑阈值而降语体的改动，直接判「要改」。

### §5.5 读者是非技术岗时，系统术语必须翻译成办事语言

> **来源：2026-07-29 实战，企业审批流程梳理汇报件。**

§5.3 管的是语体往下掉（口语渗入），本节管的是语体往旁边偏（**术语渗入**）。同一件事实，写给系统管理员和写给业务领导是两种语言。从后台配置、接口返回、代码里读出来的事实，原样落进公文就是术语泄漏——读者不是不懂那件事，是不懂你用来描述那件事的词。

**判据一句话：凡是只有在那个系统里才成立的词，都要翻译。** 自查方法是问一句「不用这个系统的人会怎么说这件事」。

| 病（系统语言） | 正（办事语言） |
|---|---|
| 节点 | 环节 |
| 表单字段 / 判定字段 | 填报内容 / 填报的执行部门 |
| 触发条件 | 经办情形 / 什么情况下经过 |
| 并行会签 | 同时发起、互不等待 |
| 路由 / 分支规则 | 分情形办理 |
| 总开关 | 决定流程走向的一项 |
| 必经 | 一律经过 |
| 走 A 线 / B 线 | 属第一类变更的 |
| 加签职能部门 | 增加职能部门审签 |
| 轻量快速通道 | 办理环节较少、周期较短 |

段落级正反例（同一段事实的两种写法）：

| 病 | 正 |
|---|---|
| A 线：项目客户、签约部门、执行部门、合同、项目金额…… → 部门负责人 → 对应业务部门 → 职能部门会签 | 第一类是涉及金额、部门、预算、外聘、采购的变更，包括项目客户、签约部门、执行部门、合同、项目金额……此类变更先经部门负责人审核，再经与变更内容对应的业务部门审核，最后由职能部门会签。 |

> 病例同时踩中 [`anti-ai-taste-anchors.md`](anti-ai-taste-anchors.md) §1.4.112「数学符号代替自然语言」。用箭头串流程是从流程图里带出来的写法，图里合法，正文里不合法。

配套三条边界：

**一是业务行话不算术语，不要翻译过头。** 会签、或签、抄送、退回、加签是审批业务本身的词，办事人天天在用。该做的是首次出现时用一句话说清含义（会签指全部签字方可通过，或签指任一人签字即可通过），不是把它换掉。**翻译的边界是「系统实现词」，不是「业务专有词」**；把业务专有词也翻译掉，稿子会变得又长又不准。

**二是系统兜底逻辑不进汇报件。** 配置里为使流程闭合而存在的默认分支、自动拒绝节点、去重开关，是实现细节不是管理事实。写进去，读者会把它当成一条管理规定来追问，凭空制造伪问题。

**三是读配置得来的观察不等于待办。** 从后台读出的异常（某开关未开、某角色为空、两处口径不一致）留在底稿备查，汇报件只写现状。汇报件里出现「建议确认」「待核实」，等于把作者没做完的活推给读者——**交付件不留待确认事项**。

**本节不得写成脚本规则。** 节点、字段、路由、触发条件在技术文档里全部合法，字面拦截必然大面积误伤；本节靠 reviewer 结合 §1 问题一（读者是谁）判断。

## §6 为什么必须派 reviewer

> **本节是流程铁律，不是建议。**

本焦点的绝大多数问题**没有固定词形**：

| 问题类型 | grep 能抓吗 | 为什么 |
|---|---|---|
| 命令式口吻 | 部分 | 「应」「必须」能搜，但「建议协会尽快……」搜不到 |
| 批评既往 | 部分 | 「尚未」能搜，但「一直以来的做法」搜不到 |
| 替客户判断 | 否 | 「符合要求」在别处完全合法 |
| 自证清白 | 否 | 「这两条在官方文件里都能落到白纸黑字」不含任何禁用词 |
| 自我宣告过渡 | 部分 | 固定句式能搜，自造的搜不到 |
| run-in 标题语体错位 | 否 | 「名单本身写着政务云」每个字都是正常汉字 |
| 章节标题不对仗 | 否 | 需要横向比较同级标题 |
| 口语渗入 | 部分 | 词表能覆盖已知的，新造的覆盖不了 |
| 术语渗入（§5.5） | 否 | 节点、字段、路由在技术文档里全部合法，字面拦截必然误伤，只能结合读者身份判断 |

**因此**：

1. **Polish 模式下，脚本 PASS 不等于稿子过关。** 脚本只是 L1，覆盖的是有固定词形的那一层。
2. **≥ 500 字的稿子，必须派至少一个 clean-context reviewer，且 focus 必须包含「口吻与站位」。** 不派 reviewer 就宣布通过 = 违规。
3. **主对话自己不能替代 reviewer。** 主对话写了这稿，对自己的措辞已经脱敏，看不出语体错位——这正是 2026-07-28 的失误机理：主对话跑完三道脚本闸门全绿，宣布通过，用户一眼看出两处论证旁白式小标题。
4. **reviewer 的 prompt 必须注入 §1 两个前置问题的答案。** 不告诉 reviewer「谁写给谁看」，它判不了口吻。
